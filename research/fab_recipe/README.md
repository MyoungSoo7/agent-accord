# 연구 1 — ACCORD × 팹 레시피 변경 승인

장비 IoT 신호를 보는 에이전트가 레시피 변경을 *제안*하고, 승인은 엔지니어만 한다. 이 구조를 실제 `accord.py` 위에 올리고, 시뮬레이션으로 그 값과 대가를 잰다.

## 질문

1. 팹 레시피 변경에 ACCORD 의 "에이전트는 좁히기만, 승인은 사람만" 을 그대로 쓸 수 있는가. 쓰려면 계약에 무엇이 더 있어야 하는가.
2. 사람 승인을 남겨 두면 품질 손실이 얼마나 나는가. 그 손실을 승인을 없애지 않고 줄일 수 있는가.
3. 그 대가는 무엇인가.

## 결론 먼저

- **승인을 없애지 않아도 손실은 없앨 수 있다. 에이전트가 승인 지연만큼 먼저 제안하면 된다.** 승인 지연 중앙값이 8시간일 때, 상한에 묶인 *뒤에* 제안하면 규격 밖 웨이퍼가 1000매당 33.38매다. 승인 지연의 90번째 백분위에 1시간을 더한 만큼 *미리* 제안하면 6.33매다. 승인 없이 즉시 적용하는 자율 정책은 5.41매다 (마모가 직선일 때).
- **대가는 사람에게 가는 제안 수다.** 마모가 예측을 벗어날수록 커진다. 랜덤워크가 강하고(σ 0.05) 승인 지연이 8시간이면 제안이 100패드당 81.4건에서 144.5건으로 늘고, 그중 31.0건은 그대로 두었어도 필요 없던 제안이다.
- **승인 단계가 실제로 막는 것이 있다.** 마모가 아니라 계측 오프셋이 같은 신호를 만든 사례에서, 사람 검토를 거친 경로는 규격 밖 0매였다. 자율 경로는 327매였다.
- **계약만으로는 안 되는 것은 상대 에이전트의 검토가 잡는다.** 첫 초안의 검증 규칙("qual 5매로 Cpk ≥ 1.33")은 아무 문제 없는 공정도 50.6% 확률로 떨어뜨린다. 계약은 형식만 보므로 이것을 못 잡는다. 상대 에이전트의 체크리스트가 쟁점으로 잡았다.
- ACCORD 에 돌려줄 발견이 넷 있다. 하나는 v2 요구사항 문서의 구멍 **P10 을 실행으로 재현**한 것이다 ([아래](#accord-에-돌려줄-것)).

## 구성

```
 CMP-03 (시뮬레이터)        A: 장비기술 에이전트 'eqp'             B: 공정통합 에이전트 'integ'
 ─────────────────          ───────────────────────────            ───────────────────────────
 패드 마모 → 제거율 ↓   →   R2R 상한 고정/예측 감지                 공정 창 파일 sha256 대조
 R2R(EWMA) 연마 시간 조정    recipe_change 초안 → 계약·본문 규칙  →  체크리스트 → question
 계측(잡음·오프셋)           revise (쟁점 반영)                 ←    revise 수신
                                     │                                     │
                              사람 1001 이 직접 친 한 줄             사람 2002 가 직접 친 한 줄
                                     └──────── approve_relay ↔ ────────────┘
                                              agreed → 적용 → qual → execute
```

## 무엇을 더했나

### 합의 대상 `recipe_change` ([`contracts/recipe_change.schema.json`](../../contracts/recipe_change.schema.json))

| 항목 | 뜻 | 필수 |
| --- | --- | --- |
| `tool`, `recipe{id, base_rev}` | 어느 장비의 어느 레시피 판본을 바꾸는가 | 예 |
| `kind` | `baseline`(기준값) · `r2r_bounds`(R2R 허용 범위) · `controller`(제어기 설정) | 예 |
| `trigger{source, signal, evidence[]}` | 무엇을 보고 제안하는가. 근거 1개 이상 | 예 |
| `changes[]{param, unit, from, to, window{lo,hi}, max_step?}` | 무엇을 얼마나. 승인된 공정 창과 한 번에 움직일 수 있는 폭 | 예 |
| `window_ref{kind, value, sha256}` | 공정 창 값의 출처. **sha256 필수** | 예 |
| `rollback{to_rev, when}` | 어디로, 언제 되돌리는가 | 예 |
| `verification[]{metric, rule, n_wafers ≥ 1}` | 무엇으로 통과를 판정하는가. 매수까지 | 예 |
| `risk`, `summary` | | 예 |
| `applies_to` | 언제까지 적용하는가 | 아니오 |

### 본문 규칙 — 스키마로는 못 거는 조건 ([`accord.py`](../../accord.py) `recipe_change_rules`)

스키마를 통과한 뒤에 돌고, 어기면 계약 위반과 똑같이 **제안 자체가 안 된다** (`propose`·`revise`·수신 봉투 모두).

| 시도 | 결과 |
| --- | --- |
| `to` 가 승인된 공정 창 밖 | 거부 — "창 밖 값은 제안할 수 없다" |
| `window` 의 lo ≥ hi | 거부 |
| `from == to` | 거부 — 바뀌는 것이 없는 항목 |
| `\|to − from\| > max_step` | 거부 |
| 같은 `param` 이 두 번 | 거부 — 어느 값이 맞는지 정할 수 없다 |
| `NaN` · `Infinity` (json 이 그대로 읽어 들인다) | 거부 — 창 비교를 무력화하므로 |
| `rollback.to_rev ≠ recipe.base_rev` | 거부 — 되돌릴 곳은 지금 승인된 판본이어야 한다 |
| 원장의 현재 판본이 위 규칙을 어김 (손으로 고친 원장) | 경고 — "원장을 직접 손댄 흔적이다" |

미니 검증기에는 `minimum`·`maximum` 을 더했다 (v2 작업 계획 1.2 와 같은 뜻이다). `accord.py` 는 여전히 표준 라이브러리만 쓰고, 새 import 는 없다.

## 모델·가정

수치는 전부 가정이다. 실제 팹 데이터로 보정하지 않았다.

| 항목 | 값 |
| --- | --- |
| 공정 | 산화막 CMP. 제거량 목표 5000 Å, 규격 4850–5150 Å |
| 제거량 | 제거율 × 연마 시간 + 공정 잡음 N(0, 30 Å). 계측 잡음 N(0, 15 Å) |
| 새 패드 제거율 | N(50, 1) Å/s. PM 뒤 qual 3매로 첫 추정 |
| 패드 마모 | 웨이퍼당 제거율 감소. 패드마다 로그정규(중앙값 0.005 Å/s, σ_log 0.35) + 랜덤워크 σ ∈ {0, 0.02, 0.05} Å/s |
| PM | 1400매마다 패드 교체. 넓힌 상한은 PM 때 r41 로 복귀 |
| R2R | 제거율 EWMA(λ 0.3), 연마 시간 = 목표/추정 제거율. 판본 r41 의 허용 범위 90–115 s |
| 공정 창 · 한 걸음 | 80–130 s ([창 파일](windows/CMP-03_OX_CMP_STD.json)) · 10 s |
| 처리량 | 시간당 30매 |
| 사람 승인 지연 | 로그정규, 중앙값 ∈ {0.5, 2, 4, 8} h, σ_log 0.5 |
| 사람이 직접 변경안을 쓰는 시간 | 로그정규, 중앙값 2 h |

정책 다섯 가지. 같은 패드에는 같은 난수를 쓴다(공통 난수). 그래서 정책 사이 차이는 짝지은 비교다.

| 정책 | 제안 시점 | 적용 시점 |
| --- | --- | --- |
| 아무도 안 바꿈 | — | — (PM 까지 대기) |
| 사람 SPC | EWMA 관리도 이탈 + R2R 이 상한에 묶여 있음 | + 작성 시간 + 승인 지연 |
| 에이전트 반응형 | 상한 고정 5매 연속 | + 승인 지연 |
| 에이전트 예측형 | 최근 150매의 추정 제거율에 직선을 맞춰, 상한 도달까지 남은 웨이퍼 ≤ 승인 지연 P90 + 30매일 때 (빗나가면 반응형으로) | + 승인 지연 |
| 자율 (비교용) | 반응형과 같음 | 다음 웨이퍼 (승인 없음) |

모든 제안은 한 걸음(+10 s, 창 상한 130 s 까지)이다. 에이전트가 낸 초안은 매번 `accord.payload_errors` 로 계약·본문 규칙을 통과하는지 확인했고, 거부된 초안은 전 조건에서 0건이었다.

## 결과

패드 1000장 × 1400매, 시드 20261010. 전체 표는 [`results.md`](results.md), 원자료는 [`results.json`](results.json) 이다.

### 1. 승인 지연과 품질 손실 — 마모가 직선일 때 (랜덤워크 0)

그대로 두면 61.7% 의 패드가 PM 전에 상한에 닿는다 (중앙값 W1039).

| 정책 | 0.5 h | 2 h | 4 h | 8 h |
| --- | --- | --- | --- | --- |
| 아무도 안 바꿈 | 81.36 ± 8.31 | ← | ← | ← |
| 사람 SPC | 7.16 ± 2.16 | 12.72 ± 2.78 | 25.70 ± 4.01 | 50.60 ± 6.01 |
| 에이전트 반응형 | 5.41 ± 1.96 | 5.97 ± 2.07 | 11.74 ± 2.89 | 33.38 ± 4.93 |
| 에이전트 예측형 | 5.41 ± 1.96 | 5.41 ± 1.96 | 5.47 ± 1.96 | 6.33 ± 2.29 |
| 자율 (승인 없음) | 5.41 ± 1.96 | ← | ← | ← |

단위는 규격 밖 웨이퍼 /1000매, ± 는 95% 신뢰구간이다. 예측형에서 반응형을 뺀 짝지은 차이는 2 h −0.56 ± 0.27, 4 h −6.27 ± 1.37, 8 h −27.05 ± 3.64 다.

- 바닥값 5.41 은 승인과 무관하다. 자율 정책도 같다. 대부분은 창 상한(130 s)까지 다 쓰고도 모자란 패드(반응형 7.1%)에서 나온다. 거기서부터는 레시피로 할 수 있는 일이 없고 PM 을 당겨야 한다.
- 손실이 커지기 시작하는 지점은 "상한에 묶인 뒤 평균이 LSL 까지 가는 시간" 과 승인 지연이 비슷해질 때다. 마모율별로 5.4 h(0.008) – 6.7 h(0.0065) – 8.7 h(0.005) – 10.9 h(0.004) 다.
- 사람 SPC 가 반응형보다 나쁜 이유는 둘이다. 발견이 늦고(상한 도달 뒤 중앙값 58매, 반응형은 25매), 사람이 변경안을 쓰는 시간이 더해진다.
- 승인이 PM 뒤에 도착해 쓸모없어진 제안은, 승인 지연 8 h 에서 반응형 100패드당 32.2건, 사람 SPC 37.4건이다.

### 2. 예측의 대가 — 마모가 직선에서 벗어날수록

승인 지연 8 h, 100패드당:

| 랜덤워크 σ | 정책 | 규격 밖 /1000매 | 제안 | 불필요 제안 | 쓰이지 않은 확대 | 창 소진 패드 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 반응형 | 33.38 ± 4.93 | 74.1 | 0.0 | 0.0 | 5.1% |
| 0 | 예측형 | 6.33 ± 2.29 | 86.2 | 5.3 | 7.5 | 8.5% |
| 0.02 | 반응형 | 35.95 ± 5.13 | 75.7 | 0.0 | 0.0 | 5.4% |
| 0.02 | 예측형 | 7.15 ± 2.40 | 107.0 | 16.5 | 27.1 | 11.2% |
| 0.05 | 반응형 | 46.13 ± 6.08 | 81.4 | 0.0 | 0.3 | 7.1% |
| 0.05 | 예측형 | 10.42 ± 2.95 | 144.5 | 31.0 | 72.5 | 23.3% |

- "불필요 제안" 은 그대로 두었어도 PM 전에 상한에 닿지 않았을 패드에 나간 제안이다. "쓰이지 않은 확대" 는 승인돼 적용됐지만 PM 까지 넓힌 만큼을 한 번도 쓰지 않은 확대다.
- 품질은 지켜진다 (σ 0.05 에서도 반응형 대비 −35.72 ± 4.31). 대신 사람이 승인할 건수가 늘고, 자동화가 움직일 수 있는 범위(상한)가 필요 이상으로 넓어진다. 창을 끝까지 쓴 패드가 7.1% 에서 23.3% 로 는다. 예측형은 이 열에 예측 신호로 창 끝에 닿은 경우까지 센다.
- 100패드는 시간당 30매로 장비 한 대가 약 194일 도는 양이다 (140,000매).

### 3. 계약이 못 잡는 것 — 검증 규칙의 오판정

R2R 이 도는 상태에서 계측값의 표준편차는 36.40 Å 이다 (이론 √((30²+15²)(1+λ/(2−λ))) = 36.38). Cpk 는 1.373 으로 1.33 기준에 붙어 있다. 이 정상 공정이 검증 규칙에 떨어질 확률:

| 매수 | Cpk ≥ 1.33 | 평균 5000±50 Å | 표준편차 ≤ 73 Å | 첫 초안 규칙 (평균+Cpk) | 고친 규칙 (평균+표준편차) |
| --- | --- | --- | --- | --- | --- |
| 5 | 50.6% | 0.01% | 0.60% | 50.6% | 0.61% |
| 25 | 45.5% | 0.00% | 0.00% | 45.5% | 0.00% |
| 50 | 40.2% | 0.00% | 0.00% | 40.2% | 0.00% |
| 100 | 33.9% | 0.00% | 0.00% | 33.9% | 0.00% |
| 200 | 26.4% | 0.00% | 0.00% | 26.4% | 0.00% |

- 기준이 공정의 실제 능력에 붙어 있으면 Cpk 판정은 매수를 늘려도 동전 던지기에 가깝다 (200매에서도 26.4%).
- 시연에서 B 에이전트가 이 쟁점을 걸었고, A 가 qual 은 평균·산포로, 적용 뒤는 SPC 관리도로 보도록 고쳤다. 시연의 적용 뒤 200매는 SPC 이탈 0회였는데 같은 구간 Cpk 는 1.23 이었다. "Cpk < 1.33 이면 rollback" 이었다면 정상 공정을 되돌렸을 것이다.

### 4. 승인 단계가 막는 것 — 계측 오프셋 사례

W700 부터 계측이 −150 Å 어긋난다 (마모율 0.0065, 승인 지연 2 h). R2R 은 얇게 읽힌 값을 따라 실제로는 과연마하고, 곧 상한에 묶인다. 마모와 같은 신호다.

| 정책 | 규격 밖 웨이퍼 | 제안 | 적용 | 검토에서 반려 |
| --- | --- | --- | --- | --- |
| 아무도 안 바꿈 | 393 | 0 | 0 | 0 |
| 에이전트 반응형 → 사람 승인 | 0 | 3 | 1 | 1 |
| 자율 | 327 | 2 | 2 | 0 |

- 승인 대기 동안 상한이 과연마를 막고 있었고, 검토에서 계측 어긋남을 찾아 첫 제안을 반려했다. 자율 정책은 상한을 넓혀 잘못된 계측값을 끝까지 따라갔다.
- 이 사례는 통계가 아니라 한 경로다. **사람 검토가 기준 계측으로 어긋남을 찾는다고 가정했다.** 사람이 그것을 못 찾으면 이 차이는 없다.

### 5. 시연 — 실제 `accord.py` 로 한 건 ([`demo_transcript.txt`](demo_transcript.txt))

```
## 2. A 에이전트의 첫 초안 — PM 까지 한 번에, 여유 10% 를 얹어
상한 115 → 133 s 제안 → 종료 코드 2
거부: recipe_change 본문 계약 위반:
  - $.changes[0].to: 승인된 공정 창 [80.0, 130.0] 밖이다 (받은 값 133.0) — 창 밖 값은 제안할 수 없다
  - $.changes[0]: 한 번에 바꿀 수 있는 폭 max_step 10.0 을 넘는다 (|133.0 - 115.0| = 18.0)

## 4. B 에이전트 검토 — 공정 창 파일 sha256 대조, 체크리스트
쟁점: 연마 시간을 늘리면 가장자리 과연마로 웨이퍼 내 균일도(WIWNU)가 나빠질 수 있는데 검증 항목에 균일도 기준이 없다
쟁점: 5매로 Cpk ≥ 1.33 을 판정하면 아무 문제 없는 공정도 51% 확률로 떨어진다 (…)
쟁점: 적용 범위(applies_to)가 없다 — 넓힌 상한을 언제 원래 판본으로 되돌리는가

## 7. 사람 승인 — 각자 자기 에이전트에게 한 줄
[eqp] 상태 agreed · 승인 eqp, integ · 전언으로 센 것 eqp, integ
[eqp] ※ 내 사람의 승인까지 '전언' 으로 보인다 — … (v2 요구사항 문서의 P10, 여기서 실행으로 재현)
```

협의 번호·지문·시각은 실행할 때마다 바뀐다. 공정 수치는 시드로 고정이다. 사람이 치는 승인 줄은 시연이라 스크립트가 넣는다.

## 해석 — 현장에서

- **자동화의 경계를 사람이 정하고, 그 안은 자동화가 움직인다.** R2R 은 매 웨이퍼 레시피를 바꾸지만 그건 이미 승인된 범위 안이다. 사람 승인이 필요한 것은 범위 자체를 바꿀 때다. `recipe_change` 의 `kind: r2r_bounds` 가 그 자리다.
- **승인 지연은 없앨 대상이 아니라 앞당겨 덮을 대상이다.** 예측형 정책의 지평을 승인 지연 분포(P90)에 맞추면 자율과 거의 같은 품질이 나온다. 그러려면 승인 지연 분포를 실제로 재야 한다. 교대·주말에 따라 달라지는 그 분포가 에이전트의 설정값이다.
- **예측을 얼마나 믿을지는 사람 부담과 맞바꾼다.** 마모가 불규칙한 장비일수록 불필요 제안이 늘어난다. 장비별 마모 예측 오차를 보고 지평을 줄이거나, 불필요 제안의 비율을 운영 지표로 둔다.
- **창 밖은 레시피의 일이 아니다.** 창을 다 쓴 패드(반응형 기준 5.1–11.2%)는 PM 을 당겨야 한다. 이 시뮬레이션에는 그 선택지가 없다. 실제로는 `recipe_change` 와 다른 종류의 협의(보전 일정)로 올라가야 한다.

## ACCORD 에 돌려줄 것

1. **P10 실행 재현.** v2 요구사항 문서는 P10(내가 보낸 `approve_relay` 가 내 원장에서 내 승인을 "전언" 으로 덮어씀)을 "코드 판독, 실행 재현은 안 함" 으로 적었다. 시연에서 양쪽 모두 자기 사람 승인을 "전언으로 센 것" 에 넣고 틀린 경고를 띄웠다 (7단계). 고치는 일은 v2 요구사항 6 에 맡기고 여기서는 손대지 않았다.
2. **2인 고정.** 레시피 변경은 보통 장비·공정·품질 세 기능의 승인을 받는다. 시연은 둘로 줄였다. SPEC §9 의 정족수 일반화가 이 도메인의 첫 요구다.
3. **승인을 장비 상태에 묶어야 한다.** v2 의 승인 만료는 시간(기본 72 h)이다. 이 시뮬레이션에서는 승인이 PM 뒤에 도착하는 일이 100패드당 최대 37.4건이었다. 그 승인은 이미 없어진 패드 상태에 대한 것이다. 본문에 장비 상태(예: 패드 누적 매수, PM 번호)를 넣어 지문이 그 상태에 묶이게 하고, `execute` 때 그 상태가 아직 맞는지 확인하는 자리가 필요하다.
4. **계약은 형식을, 검토는 타당성을.** `n_wafers` 를 필수로 둔 덕에 B 의 검토가 "5매 Cpk" 를 숫자로 따질 수 있었다. 판정 통계(평균·산포·Cpk)를 계약의 열거값으로 두고 통계별 최소 매수를 본문 규칙으로 거는 것이 다음 단계다. 단, 표 3 처럼 Cpk 는 매수만으로 해결되지 않는다.

## 한계

- 모든 수치는 위 가정의 시뮬레이션이다. 실제 팹 데이터로 보정하지 않았다.
- 마모는 직선 + 랜덤워크다. 길들이기 구간, 수명 말기의 가속, 컨디셔너 디스크 마모, 슬러리 로트 교체는 없다.
- 승인 지연은 일과 무관한 로그정규다. 실제로는 교대·주말·대기열과 엮인다.
- 제안은 항상 한 걸음이다. 필요한 만큼만 올리는 선택, PM 당김 제안은 넣지 않았다.
- B 의 검토는 규칙 기반 체크리스트다. LLM 검토자의 행동은 모델에 없다.
- 계측 오프셋 사례는 한 경로이고, 사람 검토가 오프셋을 찾는다고 가정했다.
- 균일도(WIWNU) 모델은 가정이다.
- 승인 줄은 시연에서 스크립트가 넣었다. 실제 사람 승인 경로(채팅, 신원)는 시험하지 않았다.
